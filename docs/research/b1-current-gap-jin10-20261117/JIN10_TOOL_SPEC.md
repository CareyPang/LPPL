## 2. 可复制的机制与不能推定的部分

可实现的是工具的公开数学功能及自行设计的交互：参数输入、结果预览、单位解释、公式抽屉、结果对照和资产上下文带入。**本轮没有读取金十源码、私有API合同、数据供应协议或完整后台计算链。不能将下文写成“金十就是这样实现”。** 金十官方快讯可确认国内外黄金价差采用同为元/克的比较呈现，但不能由此确定其完整取价、汇率、税费和时间对齐算法。[公开快讯示例](https://flash.jin10.com/detail/20261016150800567800) 该快讯属于国内外升贴水；目录第5项实测为固定美元金价下的汇率变化贡献，不能混为同一工具。

独立工具不需要等待金十数据采购：用户手动输入数值时直接本地计算；自动填价则必须走现有已核对的数据适配器。工具提供方、数据提供方、方法来源是三个字段。没有自动报价时保持手动模式，不能偷偷从金十抓取以填满页面。

## 3. 共享模块及边界

### 3.1 入口与状态

- 放在“市场 → 工具”或搜索结果的工具分组；个股/指数工作站提供上下文入口。不得把27工具都升成顶栏。
- 桌面用输入区＋结果区＋可展开公式/来源。390px顺序为输入→结果→细节，修改输入保留原值；返回资产恢复原图表视野。
- 手动工具默认可立即用，不因报价、AI或历史任务失败而不可用。修改数值只重算纯函数，不启动LPPL或104周回放。
- 切换“自动参考值/手动输入”要明确显示。自动报价到达时不覆盖用户正在编辑的手动数值。
- 计算参数不默认上传；仅用户明确保存账本或分享时才使用对应持久化路径。分享链接不能包含账户、精确私人资产或令牌。

## 4. 汇率换算与人民币价差

### 4.0 本轮真实操作

**VERIFIED（主代理Chrome）：** 登录后工具在约430px宽独立窗口打开。使用自定义数字键盘输入100 CNY，界面显示USD15.0451、EUR13.7067、JPY2405.81、HKD118.04，各币种有银行/购汇标识。展开USD选择器后可见“货币／汇率源／结售”三列，来源含工商、交易商报价、中行、建行等，结售含购汇/结汇/购钞/结钞。将USD从工商购汇改为结汇并确认，USD变为14.9669，其余币种不变。

这确认工具不仅选择币种，还按每行的报价来源与业务类型计算；**没有确认报价是否当前或准确，也未建立其买卖方向的经济含义**。主屏没有观察到时间戳。不能把所见数字当汇率真值或据其相对大小断言银行价差方向。完整深链未可靠读取，来源保留为已知[目录入口](https://datas.jin10.com/#/category/52005)，不猜造路由。

对LPPL的改进：每条输出直接带“来源、报价业务、单位基数、as-of”；交互可用币种/来源/类型分组，确认后只更新对应行。手动键盘也应支持正常键盘、粘贴、退格和无障碍，不能只做一个无法输入小数的手机式键盘。

### 4.1 纯函数

若汇率`q(A→B)`的单位是“B货币/A货币”，则`amount_B = amount_A × q`，反向为`1/q`，要求`q>0`。金额0应得到0；负金额只在明确支持的现金流模式可用。输入空白、非数值、无穷大、货币代码相同、分母0分别处理。

若原数据以EUR为共同基准，`q(A→B)=q(EUR→B)/q(EUR→A)`。两条源率必须来自同一发布日期/快照，派生交叉汇率标明“由参考汇率换算”。不能把USD/CNY字段和CNY/USD标签互换。

银行牌价另带`base_amount`（例如每100单位外币）、`cash_or_remittance`（现钞/现汇）、`bank_side`与`customer_action`。若牌价为`Q CNY / 100 FCY`，先规范为`Q/100 CNY / FCY`再计算，不能遗漏100倍。购汇/结汇是用户动作，银行买入/卖出是银行视角，映射需要来源定义；不只靠中文标签猜方向。现钞与现汇的价差、银行与交易商的可成交条件也不能混合平均。

手动验收例：100 USD、7.2 CNY/USD，应为720 CNY。共同基准例：1 EUR=1.10 USD、1 EUR=7.92 CNY，派生1 USD=7.2 CNY。均为合成fixture，不是当前报价。

### 4.2 数据与许可

ECB官方说明参考汇率通常在工作日约16:00 CET发布，并排除TARGET休市日；用途是信息参考，不是可成交报价。[ECB参考汇率](https://www.ecb.europa.eu/stats/policy_and_exchange_rates/euro_reference_exchange_rates/html/index.en.html) 页面应标“日参考汇率”，而不是把它贴进“实时汇率”标题。周末没有新发布不必自动等同数据故障；stale应根据源日历和预计发布时间判定。

ECB网站条款允许按条件使用直接取得的信息，包括准确呈现、注明ECB来源、说明派生修改；在收费材料中还须告知原数据可免费取得。第三方内容和署名论文有例外。[ECB版权条件](https://www.ecb.europa.eu/services/using-our-site/disclaimer/html/index.en.html) 这是已读条款事实，不代替对具体端点、产品用途、保存与展示的最终核验。

人民币价差不能只有一个含糊`spread`字段：定义`CNH_per_USD - CNY_per_USD`、报价点差、相对百分比和相对中间价偏离分别作为metric_id。必须记录两条腿时点和最大容忍时差；超出时差显示“不同步”，不把旧价相减伪装当前套利空间。

## 5. 时区与交易时钟

### 5.1 时差换算

**VERIFIED（主代理Chrome）：** 首次进入出现连接超时提示，点击重试后恢复。默认美东2026-11-16 22:24:37对应北京2026-11-17 11:24:37，显示晚13小时；日期选择器有年/月/日/时/分/秒，打开后取消，未修改到DST临界日。切换“伊朗”后显示晚4小时30，左侧保留约22:25:14的墙钟读数而标题变为伊朗，右侧北京变为次日02:55:14。此操作表现为重解释墙钟时刻，而非保持原UTC瞬间；时差算术一致，不据此判断数据错误。更多时区入口可见但未全部操作。

LPPL应将两个动作分清：“把同一瞬间显示为另一时区”和“改变输入时区、重新解释同一墙钟日期时间”。前者固定instant，后者固定local datetime并重新解算；按钮或模式切换必须说明，避免用户在事件回放里无意移动事件时刻。纯换算采用本地规则库，无需因服务器暂时不可达而锁住计算；默认“现在”若来自本机时钟须明确，不宣称完成授时校准。

保存的是UTC瞬间和IANA时区ID，输入是“日期＋当地时间＋时区”。不同日期可能有不同夏令时偏移，不能把纽约永远写成北京时间减13小时。IANA维护时区边界、UTC偏移和夏令时规则历史；其数据库许可主体为public domain，部分附带代码有明确例外。[IANA说明](https://www.iana.org/time-zones) [许可](https://data.iana.org/time-zones/tzdb/LICENSE)

用既有受支持的时区库或运行时能力，不引入未经检查的重依赖。记录运行时/tzdb版本；来自用户当地时间的DST空缺时刻必须提示不存在，重复时刻必须让用户指定较早/较晚偏移，不能默默任选。

验收fixture：2026-01-15纽约09:30对应上海22:30；2026-07-15纽约09:30对应上海21:30。纽约2026-03-08 02:30属于跳时空缺，2026-11-01 01:30有两种偏移；这些应在锁定tzdb后重验。

### 6.1 单位注册表

### 6.3 实测金银汇率价差：固定美元金价的FX情景

**VERIFIED（主代理Chrome）：** 第5项详情明示公式为`金价USD/ozt × (人民币汇率B - 人民币汇率A) / 31.1034768`。默认美元金价3877.57、A=6.6635（2026-11-16）、B=6.6636（标“实时”，但无具体时刻），点击计算后得到+0.0125元/克、+0.00%。点击“场景1”进入计算历史记录，显示本次2026-11-17一条；不能由此认定记录是本地存储、账户持久化或append-only。

独立复算绝对差额：`3877.57 × (6.6636-6.6635) / 31.1034768 = 0.012466677… CNY/g`，按4位小数与+0.0125一致。若百分比以A下的折算价为基准，应为`(B/A-1)×100≈0.001500713%`，可因2位小数显示为+0.00%；**该百分比分母是合理口径推断，尚未由页面说明建立**。LPPL应直接说明分母，并显示足够精度或“变化小于0.01%”，避免用户误以为没有变化。

这是静态敏感度计算：固定美元金价P，改变汇率，求人民币计价的变化。它不预测未来汇率，不包含金价自身涨跌、税费或境内外基差，不是国内升贴水，也不是金银价格比。若未来支持同时改变美元价P和汇率X，人民币/克总变化为`(P1*X1-P0*X0)/31.1034768`。可展开为`(X0*ΔP + P0*ΔX + ΔP*ΔX)/31.1034768`，分别为基期汇率下美元金价项、基期美元金价下汇率项、交叉项；采用其他分解法时明确交叉项分配规则，不能把总变化全归于汇率。

建议UI给两个场景卡A/B，每卡显示手动/参考来源、值与日期；结果先给绝对变化，再给已定义分母的相对变化和公式展开。保存情景需用户明确操作，使用`scenario_id`而非模型`forecast_id`，不得计入真实预测首次可见账本。自动B参考值更新时保留用户保存的A/B快照。

## 7. 房贷：已完成的一组实测与独立复算

实测入口：[房贷计算器](https://topic17z2k407.jin10.com/app_pages/mortgage-calculator.html)。**VERIFIED（主代理Chrome）：** 手机宽度的居中布局，按揭购房/商转公页签；按揭输入完成后进入`#result`，结果包含月供、总利息、含首付的购房总支出与逐期表；“修改条件”返回后保留输入。商转公功能 **NOT_INSPECTED**。

### 7.1 固定输入

页面默认演示输入：房屋300万元、首付90万元（30%）、公积金80万元年利率2.10%、商业贷款130万元年利率3.05%、30年360期。不是用户个人财务，不将这组利率宣传为当前适用贷款报价。

设单段本金`P`、月利率`r=年利率/12`、期数`n`。标准等额本息月供：`M=P*r/(1-(1+r)^(-n))`；`r=0`时单独取`P/n`。组合贷逐段算，再汇总；不能先对利率简单平均。期初余额`B(k-1)`、当期利息`I(k)=B(k-1)*r`、本金`C(k)=M-I(k)`、期末余额`B(k)=B(k-1)-C(k)`。

等额本金：每期本金`P/n`，第k期利息`(P-(k-1)*P/n)*r`，当期还款为二者之和。两种方式在相同本金/期限/利率下比较，不能只用“总利息小”认定更适合某用户。
