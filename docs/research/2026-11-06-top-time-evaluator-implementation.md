## 2. 标签是什么，什么时候才能知道

| 参数 | 默认值 | 含义与限制 |
|---|---:|---|
| 局部高点左/右邻域 | 10 / 10 个交易日 | 比较同一价格序列中的相对次序 |
| 阶段高点左/右邻域 | 63 / 42 个交易日 | 42用于表达本轮案例语义，不是优化得到的最佳值；另保留21对照 |
| 等高候选分组间隔 G | 5 | 精确同价候选按固定规则合组，最早候选作代表日；保存所有候选日 |
| 谷点左/右邻域 | 21 / 21 | 仅用于事后上涨段标签 |
| 谷至峰跨度 | 21–126 个交易日 | 在固定范围内选末日最近的闭合谷，再检验净上涨及未跌破该谷；不设最小涨跌幅 |
| 价格字段 | close | 可整组改为 high 对照；不能逐个事件选更有利字段。high模式的谷也是同一high序列的谷，并不偷换为low |

两侧都要有严格转折；一段全平价格不能自动成为高点。分组闭合需要检查额外G日及候选的完整依赖；孤立阶段峰通常至少到峰后47个交易日才成熟，长平台、缺失或数据迟到会更晚。保存 `support_start/end` 和 `available_session`，不把未来确认的标签当作峰前可用特征。

上涨段是**事后标签**。不再要求谷点必须在峰日已经成熟，因而不会凭这一条额外排除21–25日上涨。候选谷搜索范围及其所有依赖必须闭合；文件开头历史不足、缺失或尚未成熟时保留未知，不能视为“没有谷”或没有事件。

日历必须显式给出，缺失价格占原交易日位置；不通过删除缺失行把两个相隔多日的点拼在一起。`known[scale][i]=false` 表示该锚点的有无仍未知。未知、负例、成熟事件分开保存。默认“行当日可得”只是诊断假设；严格入口要求显式数据可用时间。每层另报已知/未知锚点数与召回分母完整性；完整已知子集的成绩不能宣传为全样本召回。

完整同口径下阶段候选属于短期候选。两层分组后通过候选集合交集建立事件家族；代表日仍可能不同，逐层按本层代表日计分。一对多链接标记歧义，不冒称完成两层联合识别。

## 3. 主评分和提前五日

对每层独立输出：成熟事件数 `E`、可判定首次主张数 `P`、联合成功数 `TP`、漏报 `FN=E-TP`、未成功主张 `FP=P-TP`，以及召回 `TP/E`、精确率 `TP/P`。分母为零写空值，不写成满分。这里FP包括错窗、太宽或迟到等未达到联合要求的主张，不能误解成它们附近一定完全没有高点。

主成功要求同时满足：

1. 当时明确提出对应层级，并使用其首条区间。
2. 目标是实际可行动日之后、H=63日内的下一同层事件；预测区间不能参与挑选有利目标。扫描途中若有未知锚点，停止并记待定。
3. 首条区间覆盖该事件代表日，含两端宽度不超过10个交易日。
4. 峰日减实际可行动日至少5个交易日。
5. 默认还要求窗口起点减实际可行动日至少5日，避免把用户已来不及准备的窗口宣传为“五日前提醒”。另列仅要求峰日提前5日的 `event_only` 对照。
6. 严格评分要求可行动证据已核验且发布及时；使用完整日线数据的行动日必须晚于该日线截止日。来源自己填写的verified字段仍需外部证据支撑，程序不能认证历史真实性。

预测区间过期、逆序、非未来、超H、太宽、提前不足都保留失败原因。正式精确率只计已解决的主张，未成熟/未知行动时点另列，不能在存在待定时宣称全体结果已评价完成。

### 局部到阶段的升级

- 局部首警和阶段首警各自计时。局部早到不能给晚到的阶段升级借提前量。
- 同episode、同scope的修订不增加独立主张，不修复首警；换episode但仍匹配同一事件，保留额外提醒成本，也不能修复首条事件警报。
- `both`以阶段家族为锚，短期子主张只能匹配同一家族，不能顺手把另一个较早局部峰也算命中。
- short主指标包括明确的short以及both的同家族短期子主张；stage-only的短期附属覆盖只列诊断，不悄悄增加short分母。short之后同episode的both不重置短期首警。
- 局部和阶段都命中同一个家族，家族覆盖只算一次。升级、重复、修订通知仍各自进入用户提醒负担。

## 5. 如何复现和接入研究

从仓库根目录，在已安装本项目的环境运行，输出目录必须不存在：

```powershell
python -m research.eval.top_time --input docs/research/evidence/top-time-evaluator-20261106/v1/example_input.json --out D:/CodexData/work/top-time-example-new
python tools/lppl_top_time_evaluator_report.py --out D:/CodexData/work/top-time-evidence-new
pytest tests/test_top_time_cli.py tests/test_top_time_labels.py tests/test_top_time_scoring.py tests/test_top_time_golden.py
```

入口JSON的完整例子见新证据目录 `example_input.json`。必须声明 `schema_version`、symbol、显式sessions/prices、price_basis、calendar/price_basis/publication/input状态、forecasts、runs、protocol、mode；允许显式available_sessions、asof及评价起止索引。协议输入对象只放Protocol参数，不把输出的evaluator_version键塞回参数对象。未来端点可以越出当前已观察数据，但不能把尚未发布的预测用于当期成绩。

- `fixture`：仅SYNTHETIC输入，演示严格算术，绝不产生模型能力证据。
- `diagnostic`：允许未完成来源核验的数据；输出固定注明非真实前瞻证据，理论行动与未知行动分开。
- `strict`：要求日历、价格口径、发布来源声明VERIFIED，input_status明确为VERIFIED_LEDGER，并提供显式数据可用索引；拒绝UNVERIFIED、未证明历史PIT等矛盾输入状态。输出仍写明“来源声明的严格账本，未由程序独立认证”；不能靠切换mode升级证据。

每个预测须保存明确的层级、首警身份、区间、日线截止、发布时间及其对应交易日、行动日/证据、是否及时、可选run与升级parent。发布时间使用交易日日历的当地日期和带时区ISO时间；评分按UTC先后排序，校验日期与published_session一致。当前按明确日期入账；周末发布/复杂交易时段映射应在上游形成可审计session映射，不能直接猜索引。

输出protocol、labels、evaluation和manifest；拒绝覆盖旧目录。标签保留依赖/未知/排除账本，评分保留逐主张、逐事件、各层及运行统计。命令行strict的字段核验不等于证券实际可交易性或第三方历史发布认证。

## 6. 下一步及验收门槛

1. **先补预测账本。** 逐项核对旧记录能否证明当时层级与发布时间；无法证明的只保留时间诊断。新研究从每个历史as-of只读取当时可用输入，逐日保存预测和无信号/失败状态，不能用最终标签补层级。
2. **预先固定标签候选和对照。** 默认R42及R21语义对照、完整周期1.5、候选窗口/跨尺度规则、提醒预算先版本化。开发样本负责选择；新保留段及前瞻记录负责验证。
3. **先看阶段漏报和五日联合覆盖。** 同时公开P/FP、短期成绩、拒判、运行失败、窗口宽度、首次提前量、全窗口与event_only差异。不能为减少漏报无限增加通知，也不能把局部成功抵消阶段失败。
4. **通过研究门槛后再接两级页面。** 页面保持独立局部提示和突出阶段提示，准确展示首次日期、区间、证据状态与升级；本轮评价器不会使生产页面自动获得可靠层级预测能力。
